# Off-chain security checklist (Prompt 15, Part A)

Results from 27 Oct 2026. Re-run the commands in each row before the mainnet deploy.

| Item | Result |
|---|---|
| No plaintext signals, keys, salts or private keys in logs | API logs go through pino with `redact` on every secret field (`src/lib/log.ts`). Grep of the source for log calls that pass plaintext, keys or salts found one leak: the strategy, aggregator and execution agents wrote entry/TP/SL into their activity log. That log is owner-only, but it was still plaintext at rest before reveal. **Fixed**: activity lines now record only the side, market, validity and price. Run logs from the local stack (API, keeper, A2A demo) contain no anvil private keys and no `plaintext`/`salt`/`wrappedKey` values. Re-checked on testnet runs. |
| Auth on every non-public endpoint | Routes use `requireUser` (session / Telegram initData / API key), `ownAgent`/owner checks, or `requireInternal` (constant-time `INTERNAL_SECRET` compare). Public routes are read-only. Tests: `test/auth.test.ts`, `test/agents.test.ts` (internal routes 403 without the secret). |
| Rate limits | **Added** `src/lib/rateLimit.ts`: 300 req/min per user, agent or IP; `/auth/*` and `/me/api-keys` get a tenth; internal calls are exempt; `429` + `retry-after`. Set with `RATE_LIMIT_PER_MIN`. Test: `test/rateLimit.test.ts`. It is in-memory, so it assumes one API instance; with more instances, put it behind Redis. |
| Telegram webhook secret | The bot refuses to start in webhook mode without `TELEGRAM_WEBHOOK_SECRET`; grammY checks `X-Telegram-Bot-Api-Secret-Token` on every update (`apps/bot/src/index.ts`). |
| Internal secret rotated for prod | Production must use a fresh `INTERNAL_SECRET` (≥ 32 random bytes), `SESSION_SECRET` and `KEY_SERVICE_MASTER_KEY`. They come from the host's secret manager and are never copied from `.env`. Master-key rotation is supported via `KEY_SERVICE_MASTER_KEY_PREVIOUS`. |
| Separate wallets | Deploy uses distinct `DEPLOYER` / `RELAYER` / `KEEPER` / `CREDIT_SIGNER` / `TREASURY` keys and one key per agent (`AGENT_<NAME>_PRIVATE_KEY`). The deployer goes cold after the deploy (the admin is the timelock; `check-roles` asserts the deployer renounced). Fund each wallet with only what it needs: relayer ~5 HSK, keeper ~5 HSK, agents ~1 HSK + 20 USDT. The credit signer key belongs only in the API's secret manager. |
| Mainnet RPC selection | **Fixed**: the agents runtime and MCP server sent chain 177 to the *testnet* RPC when `RPC_URL` was unset. Both now map 31337/133/177 to `LOCAL_RPC_URL`/`HSK_TESTNET_RPC_URL`/`HSK_RPC_URL`. |
| `pnpm audit --prod` | 15 advisories at the start, all transitive. Patched with `pnpm-workspace.yaml` overrides: `ponder>vite` 8.3.5, `ponder>@hono/node-server` 1.19.15, `valibot` 1.4.2 (Telegram SDK). **4 remain, accepted:** `drizzle-orm` 0.41 pinned by ponder (identifier escaping; the indexer builds no SQL identifiers from user input, and our API uses drizzle 0.45.4), `@graphql-tools/utils` ×2 (ponder's GraphQL server; we don't expose it publicly), and `zod` 3.x via abitype (memory on huge collections; inputs are ABIs we ship). CI fails on `critical`. |
| Pinned versions | Every direct dependency is an exact version, `pnpm-lock.yaml` is committed, and CI installs with `--frozen-lockfile`. |
| `.env.example` complete | Diffed every `process.env.*` and env-schema key against `.env.example`. Added the missing ones (web `NEXT_PUBLIC_*`, MCP demo caps, agents market data, monitoring, rate limit, test DB). Only test-harness vars (`ANVIL_PORT`, `FORGE_BIN`, `WALLET_E2E`, …) are left out. |
| No secrets in git history | `git log -p --all` was grepped for private-key/secret/mnemonic assignments and for 32-byte hex values. The only hits are well-known anvil test keys and hashes in dry-run broadcasts. No `.env`, `.pem` or key files are tracked. |

## Monitoring
- `GET /status` on the API, rendered at `/status` on the web app. It shows API (DB + RPC), relayer balance, keeper balance (`KEEPER_ADDRESS`), each URL in `STATUS_SERVICES` (bot, keeper, mcp `/health`), overdue settlements (expired more than 2 h ago and not settled) and HSP verify failures in the last hour.
- The `ops.monitor` job runs every 5 minutes. When a check fails it sends a Telegram message to `ALERT_TELEGRAM_CHAT_ID`, and it sends another when the check recovers. It does not repeat alerts on every tick. Test: `test/monitor.test.ts`.
